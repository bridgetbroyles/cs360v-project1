# 2. Repository & How to Actually Use the Project

All commands below assume the course Ubuntu environment described by `SETUP.md`.
From the repository root, enter the project first:

```bash
cd project_1
```

## Build and run

```bash
cd emulator && make
```

This compiles the host emulator and links Unicorn, producing
`project_1/emulator/emulator`.

```bash
cd ../guest && make
```

This cross-compiles the freestanding x86-64 sample guests and creates flat
`.bin` images such as `test_log.bin`.

```bash
../emulator/emulator --log out.log test_log.bin
echo $?
cat out.log
```

The emulator creates the VM, loads `test_log.bin`, runs it until poweroff, returns
the guest's exit code, and writes records to `out.log`. Success normally means
exit code 0 and four correctly formatted records. Add `--trace` to print each
guest instruction address to stderr.

## Tests

From `project_1/tests`:

```bash
./run_tests.sh
```

This is the authoritative full suite. It rebuilds student code and test guests,
runs Part I micro-tests, deterministic and randomized Part II tests, then staged
and adversarial Part III tests. Our final run reported `37 passed, 0 failed` with
`P1_SEEDS=20`.

```bash
P1_SEEDS=20 ./run_tests.sh
```

This repeats each randomized MMIO scenario 20 times rather than the default 3.
It is the better final confidence check.

There is no separate official Part I or Part II script. The full script prints
them in distinct sections. To debug one deterministic guest manually:

```bash
make
../emulator/emulator --log /tmp/m.log m_stack.bin > /tmp/m.obs
diff -u expected/m_stack.obs /tmp/m.obs
```

For Part I substitute `m_boot`, `m_stack`, `m_ram`, `m_exit`, or `m_fault`.
Remember that `m_exit` and `m_fault` intentionally have nonzero expected exit
codes in `expected/*.exit`. For Part II substitute `t_discovery`, `t_log_basic`,
`t_log_levels`, `t_repeated`, `t_badcmd`, or `t_stat`, and also compare `/tmp/m.log`
with the corresponding `expected/*.log` when present. Random Part II scenarios
are generated by `oracle` and are easiest to run through `run_tests.sh`.

For Part III alone:

```bash
cd project_1/tests
./run_virtq_tests.sh
```

This compiles a synthetic two-region guest memory map and runs `translate`,
`single`, `chained`, and `indirect` at four seeds each. Success is
`16 passed, 0 failed`. The full suite additionally builds `virtq_private.c` with
AddressSanitizer and UndefinedBehaviorSanitizer for hostile rings.

For the optional real-VM integration:

```bash
cd project_1/vhost
./run-qemu.sh
```

The script builds the backend and tiny initramfs, starts the vhost-user process,
boots the host's Linux kernel in QEMU, and compares the resulting four-record log
visually with the expected block. It requires Linux, QEMU, a readable kernel, and
the matching guest compiler. A hang after one record usually means the used ring
was not published. Guest console diagnostics are in `vhost/qemu.out`.

## Clean, inspect, submit

```bash
make -C project_1/emulator clean
make -C project_1/guest clean
make -C project_1/tests clean
make -C project_1/vhost clean
```

Each removes that component's generated objects/binaries. Then rebuild and test.

```bash
git status --short
git diff --check
git diff -- project_1/emulator/vmm.c \
  project_1/emulator/device.c project_1/vhost/virtio.c
```

The first shows changed files, the second finds whitespace errors, and the third
reviews the deliverables. This assignment has no Project 1 submission script in
the repository. Submit exactly those three `.c` files through the course's
submission mechanism; do not submit modified tests or headers.

## If I had to run this project alone from scratch

- Set up the Project 0 Ubuntu VM and run `project_0/setup/setup-vm.sh`.
- Read `project_1/SPEC.md`; treat it as authoritative.
- Build `emulator`, `guest`, and `tests`.
- Run the VMM micro-tests in order; fix the first failure.
- Run device tests, then randomized tests with a larger `P1_SEEDS`.
- Run `./run_virtq_tests.sh`, then the full suite.
- Optionally run `vhost/run-qemu.sh` on Linux.
- Run `git diff --check` and confirm only the three deliverables changed.
- Submit `vmm.c`, `device.c`, and `virtio.c`.
